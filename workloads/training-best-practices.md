# 训练任务最佳实践

本文面向普通用户和项目管理员，总结在 Zenith 上提交、运行和管理训练任务的推荐做法。如果你是第一次提交训练任务，建议先阅读[训练任务快速开始](/workloads/training-quick-start)。

## 从开发机到训练任务的标准工作流

1. **在开发机中验证环境和代码**
   - 使用与训练任务相同或相近的镜像创建开发机。
   - 确认数据路径、依赖版本和启动命令都能正常工作。
   - 先用少量数据和较短的训练步数做“冒烟测试”。

2. **准备可重复运行的启动命令**
   - 使用绝对路径。
   - 不依赖交互式输入。
   - 把超参、随机种子等写在配置文件或命令行参数中。

3. **提交训练任务**
   - 先开启 仅校验 校验参数。
   - 关闭 仅校验 后正式创建。
   - 观察任务状态、日志和事件。

4. **保存结果并清理资源**
   - 确认检查点和日志写入持久存储。
   - 停止或删除不再需要的任务。
   - 保留开发机用于分析，或适时停止。

## 启动命令最佳实践

### 使用绝对路径

训练容器的工作目录可能与开发机不同。始终使用挂载点的绝对路径：

```bash
python /personal_fast_storage/my-project/train.py \
  --data_dir /datasets/my-dataset \
  --output_dir /personal_fast_storage/my-project/outputs
```

### 避免硬编码环境信息

- 不要写死节点 IP、主节点地址、节点编号或 WORLD_SIZE。
- 使用平台注入的环境变量，例如火山 MLP 的 `MLP_WORKER_NUM`、`MLP_WORKER_GPU`、`MLP_ROLE_INDEX`、`MLP_WORKER_0_HOST`、`MLP_WORKER_0_PORT`。
- 不要覆盖这些 `MLP_*` 变量。

### 处理检查点恢复

训练程序应自行管理检查点恢复：

```bash
python train.py --resume_from /personal_fast_storage/my-project/outputs/checkpoint-latest
```

低优任务被抢占后，平台会自动重新排队并重新执行原命令，但不会自动从上次进度恢复。程序必须自己检测已有检查点并继续训练。

### 把日志写入持久存储

不要把训练日志只输出到控制台。同时写入持久存储：

```bash
python train.py --log_dir /personal_fast_storage/my-project/logs 2>&1 | tee /personal_fast_storage/my-project/logs/train.log
```

实时日志窗口最多保留约 5,000 行、200 万字符，不能替代持久日志文件。

### 不要在命令中包含凭据

- 不要把密码、AK/SK、API Token 直接写在启动命令中。
- 如需访问外部服务，通过环境变量或挂载的密钥文件传入，并确保这些文件位于安全的只读挂载中。

## 镜像选择最佳实践

- **与代码匹配**：选择包含正确 PyTorch、CUDA、Python 和依赖版本的镜像。详见[如何选择合适的镜像](/assets/choosing-images)。
- **使用项目镜像**：团队协作时，使用项目登记的镜像，保证所有成员环境一致。
- **避免频繁切换镜像**：同一组实验尽量使用同一镜像，减少环境差异带来的不确定性。
- **保存稳定环境**：当开发机中安装了复杂依赖且验证通过后，保存为镜像，避免每次重新配置。

## 存储挂载最佳实践

### 数据

- 训练数据建议放在只读数据集、个人存储或项目存储中。
- 不要把整个数据集复制到容器临时目录，而是直接读取挂载路径。
- 多个节点同时读取同一数据集时，确保挂载是只读或支持并发读取的。

### 输出和检查点

- 输出目录必须位于可写的持久存储，例如个人存储或项目存储。
- 建议按任务命名输出目录，避免不同任务互相覆盖：
  ```bash
  --output_dir /personal_fast_storage/my-project/outputs/exp-$(date +%Y%m%d-%H%M%S)
  ```
- 定期保存检查点，并保留最近几个版本的检查点，不要只保留最后一个。

### 挂载路径核对

提交前务必确认：

1. 启动命令中使用的路径与创建窗口“将挂载”提示中的路径完全一致。
2. 不同挂载项没有覆盖同一路径。
3. 数据挂载和输出挂载位于同一资源区。
4. 项目只读成员不会获得可写项目挂载。

## 选择标准任务还是低优任务

| 维度       | 标准任务               | 低优任务                         |
| ---------- | ---------------------- | -------------------------------- |
| 费用       | 消耗个人/项目卡时      | 不扣个人或项目卡时               |
| 稳定性     | 不会被平台主动抢占     | 可能被厂商或平台抢占             |
| 并发上限   | 受每人 64 卡等限制     | 使用独立份额规则                 |
| 适用场景   | 正式训练、需要稳定运行 | 可中断的实验、冒烟测试、调参探索 |
| 检查点要求 | 建议保存               | 必须保存到持久存储               |

::: warning 低优任务没有恢复保证
低优任务被停止后，平台会按原 GPU 申请数重新排队，但**不会自动从上次进度恢复**。训练程序必须自己从检查点继续。
:::

## 分布式训练选择

### 单节点多卡

- 使用同一节点内的多卡进行 DataParallel 或 DistributedDataParallel。
- 适合单节点就能容纳的模型规模。

### 多节点同构任务

- 通过创建窗口的 **节点数** 设置节点数。
- 所有节点使用相同的 GPU 型号、卡数和镜像。
- 适合 PyTorch DDP、Horovod 等框架。

### 多角色异构任务

- 仅平台管理员视图和运维视图支持，且受厂商能力限制。
- 火山 MLP 支持异构角色；无问芯穹只支持同构节点。
- 普通用户不需要使用此功能。

## 使用 仅校验 和复制任务

### 仅校验 流程

1. 完整填写表单。
2. 开启 仅校验，点击校验。
3. 修正参数错误。
4. 关闭 仅校验，再次核对。
5. 创建。

### 复制任务

- 对于重复性实验，使用 **复制并重新配置** 功能，避免重复填写相同配置。
- 复制后核对镜像、规格、节点数、项目、存储和启动命令。
- 如果原镜像或挂载已不可用，手动选择替代项。

## 失败排查 Checklist

当任务状态为失败或异常时，按以下顺序排查：

1. **查看任务详情中的状态信息和事件**
   - 状态时间线会记录关键事件和排队原因。

2. **查看实时日志**
   - 确认训练程序是否启动。
   - 查找 Python 报错、CUDA 错误、OOM、路径错误等。

3. **确认启动命令**
   - 路径是否为绝对路径。
   - 是否使用了正确的环境变量。
   - 是否包含凭据或敏感信息。

4. **确认镜像**
   - 镜像是否在目标资源区启用。
   - 镜像中的依赖版本是否与代码匹配。

5. **确认挂载**
   - 启动命令中的路径是否实际挂载。
   - 数据挂载是否只读、输出挂载是否可写。
   - 不同挂载是否冲突。

6. **确认资源**
   - 是否超出个人并发上限。
   - 是否因额度不足被拒绝。
   - 是否因节点碎片导致排队。

7. **使用厂商控制台**
   - 如果详情提供 **打开厂商任务控制台**，可在其中查看更底层的日志和事件。

8. **简化复现**
   - 在开发机中使用相同镜像和启动命令复现问题。
   - 先用最小数据、单卡、短步数验证。

## 成本与额度管理

- 提交前估算总 GPU 数：单节点 GPU × 节点数。
- 多节点、多角色会快速放大资源消耗。
- 定期检查个人和项目额度，避免训练中途因额度耗尽被停止。
- 不必要时选择低优任务，但务必保存检查点。
